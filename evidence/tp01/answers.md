## Part A

**A1. Why do the raw CSV, a fitted model and the training code have different roles?**
The training code is *written by us*: it is small text, reviewed and versioned in Git. The raw CSV is an *input we receive*: we never edit it, we identify it by its source URL and SHA-256 hash, and we do not commit it (it can be large or sensitive). A fitted model is an *output we generate*: it can be rebuilt from code + data + configuration, so it is stored as an artifact (later in a tracking store), not in Git. Mixing them makes it impossible to tell what was authored, what was received and what was produced.

**A2. Why would including `Churn` among the inputs invalidate the task?**
`Churn` is the answer we want to predict. If it is an input, the model just copies it and looks perfect in evaluation, but in production the label is unknown when we need the prediction. This is target leakage: the score measures nothing useful.

**B2.1 - Python constraint and a direct dependency in `pyproject.toml`:** `requires-python = ">=3.11,<3.13"`; direct dependency `numpy~=1.26.0`.

**B2.2 - The same dependency in `uv.lock`:** `name = "numpy"`, `version = "1.26.4"`, with its source (PyPI) and the SHA-256 hashes of its sdist and wheels.

**B2.3 - A transitive dependency (`uv tree`):** `scipy 1.17.1`, pulled in by `scikit-learn`; also `python-dateutil` via `pandas`. We never asked for them directly.

**B2.4 - `pyproject.toml` vs `uv.lock` vs `.venv/`:**
- `pyproject.toml` = what the project *needs*: allowed ranges, written by hand.
- `uv.lock` = what was *resolved*: the exact version + hash of every package (direct and transitive), generated by uv. Both are committed.
- `.venv/` = the environment actually *installed* on one machine from the lock. It is generated, platform-specific and never committed.

**B3 - `numpy ~= 1.26.0` vs `numpy == 1.26.4`:** `~= 1.26.0` means `>=1.26.0, <1.27.0`, so several versions are allowed. `== 1.26.4` allows exactly one. The range lives in `pyproject.toml`; the lock records the version actually chosen (1.26.4).

## Part C

Observed values (`evidence/tp01/data-overview.json`) match the expected ones: 7,043 rows, 21 columns, `No` = 5,174, `Yes` = 1,869 (26.54 %), 0 duplicate `customerID`, 11 whitespace-only `TotalCharges`. SHA-256 `16320c9c1ec72448db59aa0a26a0b95401046bef5d02fd3aeb906448e3055e91`.

1. **Classification:** the target `Churn` takes a finite set of categories (`Yes`/`No`). We predict a class, not a continuous quantity.
2. **Class balance and accuracy:** only ~26.5 % churn. A model that always says "No" reaches ~73.5 % accuracy while detecting no churner at all. We will need recall, precision, F1 or ROC-AUC/PR-AUC.
3. **`TotalCharges` read as object:** 11 rows contain a space instead of a number. pandas cannot parse `" "` as a float, so it keeps the whole column as strings (`object`).
4. **`isna()` misses whitespace:** `" "` is a real non-empty string, not `NaN`. `isna()` only detects actual missing values. We must strip and compare with `""` (as the script does) or convert with `pd.to_numeric(..., errors="coerce")`.
5. **Proof that a teammate inspected the same file:** the same SHA-256 (in `telco.source.json` and the report), the same commit-pinned source URL, and identical inspection counts. The filename alone proves nothing.

**Extension 1 (source mismatch), observed for real:** a copy of the dataset downloaded from another link (`datasets.csv`) had SHA-256 `62ca518b...a20c`, a UTF-8 BOM and each row wrapped in quotes. Same name, same content "in appearance", different bytes: the hash check rejects it. We used the commit-pinned IBM file instead.
